# Aggregate first — 聚合优先、统计口径与非空计数

本文件展开 Entry Point 的 **Aggregate Is Statistics, Not Records** 与 **Explicit Statistical Scope**。它是分析纪律，不指定具体查询：Agent 仍自主决定用哪个聚合、要不要分组、展示多少组。

## 为什么聚合优先

聚合结果**小**、**必然完整**、**不会被行数截断**。一个 `SELECT COUNT() FROM X WHERE ...` 只回一个数，无论 `X` 有 800 行还是 800 万行。相比之下，明细路径的成本随数据量增长，而且一旦被截断就必须重新声明覆盖率。

因此判断顺序是：**这个问题能不能只用一个或几个统计量回答？** 能，就不要走明细。

| 用户问题 | 最小充分证据 |
| --- | --- |
| 一共有多少条 | 完整范围的 `COUNT()` |
| 各状态/各阶段多少条 | 完整范围的 `GROUP BY` 计数 |
| 金额情况 | 覆盖完整范围的 `SUM` / `AVG` / `MIN` / `MAX` 与非空计数 |
| 某字段是否全空 | 完整范围的 `COUNT()` 与 `COUNT(field)` 对比 |
| 时间范围 / 是否同日 | 完整范围的日期 `MIN` / `MAX`，或按日期分组 |
| 有没有某类记录 | 带该条件的 `COUNT()`，结论是「有 N 条」或「0 条」 |

具体 SOQL 必须依据当前 Schema 与当前权限动态生成。**MUST NOT** 写 SQL 风格的 `COUNT_IF` / `FILTER` 等 SOQL 不支持的语法；不支持时改用可用的等价写法。

## 标量聚合 vs 分组聚合

- **标量聚合**（无 `GROUP BY`）：Salesforce 把值放在响应自己的 `totalSize` 位置，**不返回任何行**。`query_records` 因此把值报在 `aggregateValue`，而把 `totalSize` 置为 `null`，`records` 合法为空。把空的 `records` 读成「没有数据」是错的——值就在 `aggregateValue` 里。
- **分组聚合**（有 `GROUP BY`）：每组返回一行，`totalSize` 真的是行数，`fetched` 与它可以正常比较。分组数很多时仍可能被 `MAX_ROWS` 或响应预算截断；这时收窄 `WHERE` 或减少分组维度，而不是去提高上界然后硬读。

## 统计口径必须显式

一个统计量只有带上口径才可用。**MUST** 一起给出的至少有：

- **时间窗** —— 哪一段？用什么字段界定？（边界含不含当日要能说清）
- **过滤条件** —— 排除了什么？没排除什么？
- **分组维度** —— 按什么分的组？分组之间是否互斥、是否覆盖全部？
- **币种与单位** —— 多币种 org 里，不同币种的金额不能直接相加。
- **分母** —— 这个比例的分母是哪个集合？

两个 `SUM` 在不同时间窗或不同过滤条件下**不可比较**；把它们并列陈述会造出一个不存在的对比。口径无法确定时，先确定口径，或者把结论限定在能确定的那部分上。

## 非空计数不是总数

`COUNT(field)` 是**非空计数**，**MUST NOT** 当作总记录数或比例分母。判断「是否全空」的正确做法是**同一范围**上比较 `COUNT()` 与 `COUNT(field)`：

```text
COUNT()        = 41 500
COUNT(Nope)    = 0        → 支持「该字段在这 41 500 条上全部为空」
COUNT(field)   = 12 300   → 支持「41 500 条中有 12 300 条非空」
```

- 只有非空计数为 `0` 才支持「全部为空 / 没有任何一条有值」。
- 读到前 N 条为空**不能**推断全体为空。
- 「响应里没有这个字段」**不等于**它是空值。
- `null`、空字符串、`0`、`false` 是四种不同事实，**MUST NOT** 混同。

## 聚合不是记录

聚合的输出是**统计量**。**MUST NOT**：

- 为聚合结果编造记录 Id；
- 给统计量挂一条记录链接；
- 用「这条记录」「这几条」去描述一个分组的结果行（它们是**分组**，不是记录）；
- 把标量聚合当成一个只有一条记录的列表。

呈现方式应当是「某口径下的统计结果」，并说明该口径；需要明细时另行读取，并另附覆盖率。

## 聚合也会截断

聚合不是永不被截断，只是不容易被截断。分组数极多、或每组行很宽时，`truncated` 仍然会亮，原因通常是 `MAX_ROWS` 或 `RESPONSE_BUDGET`。此时的补救是**减少分组数或行宽**（收窄 `WHERE`、少取字段），而不是提高上界硬读——提高上界只会把一个超宽的响应变成一个更大的超宽响应。
