# 诊断决策树：先分类，再取证

分类不是分类学练习，它决定**接下来调哪个 Tool**。走错类会拿到一堆真实的、但回答不了这个问题的证据，然后在错误的证据集上编故事。所以第一步永远是：把症状写下来，标出它属于下面哪一类，说出依据，再进该类路径。

一次诊断只走一条主路径。**跨类要显式换档**：说出为什么这一类解释不了、已经取得的证据哪些在新类里仍然成立、哪些作废。

---

## 归类信号表

| 类 | 典型症状说法 | 归类依据（能观察到的） |
| --- | --- | --- |
| **数据类** | 「数字不对」「少了几条」「汇总和明细对不上」「这条记录查不到」 | 症状只关于**记录的内容或数量**，读得到、写得到、权限正常 |
| **权限类** | 「看不到这个字段」「编辑不了」「按钮/入口不见了」「别人能看到我看不到」 | 症状随**身份**变化；同一条记录换个人就正常 |
| **配置类** | 「校验规则不该拦」「流程没触发」「布局/选项不对」「自动化行为变了」 | 症状关于**自动化或元数据的行为**，代码本身没报错 |
| **代码类** | 「报了个错」「页面崩了」「提示 Apex 异常」「间歇性 500」 | 有**运行时异常**；错误消息里常带类名 |
| **平台类** | 「昨晚开始就不对」「定时任务没跑」「批量处理堆住了」「全公司都这样」 | 症状**有时间起点**或**影响面超过单个用户**，且不是某个字段/某条记录的问题 |

两类都像时，按「哪一类的第一条证据更便宜」决定先后，并说明这是暂定归类。**不要**为了绕开分类而先跑一次全量查询——那既不属于任何一类，也不构成证据。

---

## 数据类 → Schema 与真实值

**问题形态**：记录的值、行数、分布、关系与预期不符。

**取证顺序**：

1. `describe_sobject`（必要时 `list_sobjects`）核对**字段的 API 名、类型、关系名、Picklist 取值**。用户说的字段名往往不是 API 名，预期本身也可能建在错误的字段上。
2. `query_records` 读真实值，并带上**覆盖率**：`fetched` 对 `totalSize`、是否 `truncated`。少了几条这类断言，没有覆盖率就不是断言。
3. 需要跨对象或关键词检索时用 `search_records`；需要全量时走 Bulk 对（`submit_bulk_query` → `get_bulk_query_results`）。

**证据要求**：字段 API 名 + 读到的行数/总量 + 具体记录标识（内部用 ID，不对外展示）。完整性口径与三条补救路径见 `sfoa-data-analysis`。

**死路**：拿一个「应该有值」的记忆当基线。基线必须来自当前 org 的证据（另一条记录、另一段时间、另一个对象的口径），不能来自模型记忆。

**升级信号**：Schema 与真实值都正常、但用户看不到/改不了 → 转**权限类**。值对、但生成它的自动化没跑 → 转**配置类**。

---

## 权限类 → 字段与对象的访问归因

**问题形态**：不可见、不可编辑、被拒，且症状随身份变化。

**取证顺序**：

1. `explain_field_access`，输入目标对象与字段（需要时带上目标用户，限于当前路由已配置的身份）。输出的是**结论 + 授权来源链 + 冲突说明**：哪条 Profile、哪个 PermissionSet、哪条直接赋值把权限给了谁，以及互相抵消的项。
2. 结论里出现的权限集/简档本身要进一步读时，用 `get_metadata_component_context`（配置类工具）取它的定义——这是**受控的跨类**，说明理由即可。
3. 记录级（共享）而非字段级的问题不在本 Tool 的范围内：先确认是字段/对象级还是记录级，记录级要走共享模型而不是字段权限。

**证据要求**：结论 **MUST** 附**授权来源链**——权限来自哪里、经由什么、被什么抵消。只说「没有权限」不算归因。结论里的 `visible` / `editable` 可能取到**不确定**这个字面值（不是 `true` 也不是 `false`）：那表示某一层根本没有被读到，**MUST** 按不确定转述并指出是哪一层，**MUST NOT** 折成 `false`。层与层之间的分歧会单独列出，引用它比笼统说「权限混乱」有用。

**死路**：把「不可见」当成 Bug。没有可见性行就是一种真实结论；先确认 Tool 的结论与 org 事实一致，再讨论它是否**符合预期**。也不要试图用一次对象级读取的结果去替代字段级归因——两者是不同的层。

**升级信号**：字段权限齐全、记录级共享也放行，但访问仍失败 → 转**配置类**（校验规则、触发器、Flow、Record Type）。`INDETERMINATE` → 见 [degradation-and-indeterminate.md](degradation-and-indeterminate.md)，不要自己挑一个来源当答案。

---

## 配置类 → 找到组件，再读它的定义

**问题形态**：校验规则、Flow、Apex 触发器、布局、Picklist、Record Type、权限集等**元数据行为**与预期不符。

**取证顺序**：

1. `list_metadata_components` 按类型列出组件：fullName、状态、最后修改者与时间。这是**发现**步骤——先证明组件存在、名字是什么、什么时候被改的。
2. `get_metadata_component_context` 读被选中组件的**定义**。一次只读真正相关的那一个（或少数几个），不要把整个类型读完。
3. 类型不在允许列表、或组件被拒绝时，把 Tool 给出的**可行动错误**（带缺失前提标识）转述给用户；**不要**换一个类型名反复试。

**证据要求**：组件 **fullName** + 最后修改时间/修改者（当结论与「什么时候变的」有关时）+ 定义中支持结论的那一段（条件、公式、顺序）。

**两个容易误判的边界**：

- **停用的组件默认不在列表里。** 「我记得有这个组件，但列表里没有」的第一嫌疑是它被停用/删除了，而不是权限或名字拼错——按 Tool 的开关把停用项一并列出再判断。列不到时，把它当作一个**前提**说出来，不要下「不存在」的结论。
- **列表没有偏移分页。** 结果被截断时，收窄靠**按名字前缀筛选**或**提高本次上限**，不是翻页；`totalCount` 是过滤之后、截断之前的匹配数，`returnedCount` 才是拿到的条数。两者一起读，不要把 `returnedCount` 当总量。

**死路**：凭组件的**名字**猜它的行为。名字相近的组件很多，行为只能从定义里读。**MUST NOT** 把组件 fullName 做规范化或改写后再引用——名字可能被本地化或转义，引用时原样回传。

**升级信号**：组件定义正常、修改时间也不在异常时间点附近 → 转**平台类**，看是否有异步失败或别的变更。定义里有 Apex 调用、且异常是运行时错误 → 转**代码类**。

## 代码类 → trace 闭环，或（不可复现时）静态路径

**问题形态**：Apex 运行时异常、页面报错、间歇性失败，错误消息里通常带类名。

**可复现时**（闭环四步，顺序不可换）：

1. `set_trace_flag` 为相关用户或类开启限时 trace。**这一步不等于拿到日志。**
2. **给出最小复现指引**（操作步骤 + `durationMinutes` 窗口期）并**等待用户复现**。见 [trace-and-reproduction.md](trace-and-reproduction.md)。
3. 复现之后 `get_apex_logs` 按时窗/用户/状态列出日志，挑出**属于这次复现**的那一条（用时间与执行者交叉确认，不要拿最近的一条顶替）。状态过滤用的是 **org 自己的状态字面量**，不是固定枚举——先看这次返回里实际出现过哪些状态，再决定要不要按状态筛。
4. `get_debug_log_body` 读该条日志的正文，定位异常类型与**行号**。异常摘要是从**整条**日志里解析出来的，即使正文因体积被截断，摘要仍可能已经指出异常类型、类与行号——所以先看摘要，再决定要不要更多正文。

**不可复现时**（历史问题）：**不要**开一个空转的 trace 然后反复拉日志。走静态路径——`get_platform_diagnostics` 看异步失败与变更时间线 → `get_metadata_component_context` 读涉事类/触发器的定义 → `explain_field_access` 排除权限因素；用户看到的错误消息里的类名就是 `list_metadata_components` 的入口。

**证据要求**：类名 + **行号** + 异常消息（原文引用，不改写）+ 触发它的那次执行的标识。只说「有个空指针」不算定位。

**死路**：把日志里的**另一条**执行的异常当成这次的答案。同一窗口里往往有多条日志，选中依据必须是「这次复现」而不是「看起来最像」。

**升级信号**：类定义与输入都正常、异常只出现在特定数据上 → 回到**数据类**核对那批数据。异常发生在批量/异步上下文里、且不是代码缺陷 → 转**平台类**看作业状态。

## 平台类 → 合并时间线

**问题形态**：有明确的时间起点，或影响面超过单个用户/单条记录；定时任务、批量作业、整体行为改变。

**取证顺序**：

1. `get_platform_diagnostics`，窗口覆盖异常起点**及其之前一段**（要能看到「变之前」的平静期，否则无法把条目与起点关联）。
2. 在合并时间线上找异常起点**之前最近**的条目，读出它的来源节、动作、操作者、时间。
3. 对时间线上的候选条目做二次取证：变更类 → 转**配置类**读该组件定义；失败类 → 转**代码类**（若可复现）或读涉事类定义。

**证据要求**：**审计条目的时间戳 + 操作者 + 动作**，以及它与异常起点的相对位置（在此之前多久）。「最近有变更」不是证据，时间戳才是。

**死路**：把时间上的相邻当成因果。相邻只是**候选**；要成为结论，还需要该条目在语义上能解释症状（改了的东西正好是出问题的东西）。

**降级语义**：某一节不可用时，**逐节**转述——哪一节读到了什么、哪一节因缺少什么前提而不可用。**不要**用一个全局的「一切正常」盖住一个没读到的节。

---

## 跨类升级的写法

换类时在回答里写清三件事：

1. **为什么原来的类解释不了**（哪条证据把它排除了）。
2. **已经取得的证据哪些在新类里仍然有效**（不要丢掉已确认的事实，也不要重新问用户一遍）。
3. **新类的第一条取证是什么**，以及它预期能回答什么。

没有这三句的换类就是漫游，用户看到的是你在挨个试工具。
