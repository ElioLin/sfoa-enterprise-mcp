# Duplicate Check（CREATE）

用于 CREATE 前对用户提供、并将直接写入目标对象的**敏感身份字段**做有界查重。目的不是实现 Salesforce Duplicate Rules，而是在写入前把「可能已经存在同一条业务对象」的事实告诉用户，由用户决定继续新建、改为更新已有记录或取消。

**不是每个字段都要查重**：只查身份键 / 业务唯一键，不查描述性、过程性或默认值字段。

## 1. 哪些字段要查

字段必须来自当前 `get_record_action_context` 的真实 `label`、`apiName`、`dataType`；**MUST NOT** 硬编码对象或字段 API 名。

| 家族 | 典型 label / API 线索 | 强度 |
| --- | --- | --- |
| 名称 | `Name`、名称、客户名称、公司名称、联系人姓名、姓名 | 弱：同名不等于同一条 |
| 手机 | `MobilePhone`、手机、移动电话、Cell | 强 |
| 电话 | `Phone`、电话、联系电话、座机、固定电话、办公电话 | 强 |
| 邮箱 | `Email`、邮箱、电子邮箱 | 强 |
| 证件 / 税务号 | 身份证号、统一社会信用代码、税号、组织机构代码 | 强 |
| 外部 ID / 编号 | 外部 ID、External ID、业务编号、客户编号、工号（仅当业务上是唯一键） | 强 |

以下**不做**例行查重：

- 备注、描述、说明、阶段、来源、日期、时间、金额、数量、Picklist、Owner、普通 Lookup。
- 地址默认不查；只有当前业务明确把地址当唯一键时才查。
- 默认值、Create Defaults、Record Type 默认、managed 值、平台生成值：不是用户提供的身份事实，不查。
- 只用于解析 Lookup 的值：例如在 Contact 上填「客户 = 某公司」，这是解析关联目标，按 [lookup-and-picklist.md](lookup-and-picklist.md) 处理；**MUST NOT** 因为该公司已存在就判定新记录重复。
- 用户没有提供、也不是从已读材料或可信上下文可靠得到的身份值：不要为了查重额外追问。

## 2. 归一化与查询

只查**将直接写入目标对象**的值。默认只在目标对象内查；跨对象（例如 Lead / Contact / Account 之间）不是硬性要求，除非用户明确要求。没有任何身份值可查时记录 `NO_IDENTITY_VALUE`，不要为了查重额外追问或发起空查询。

**归一化口径：**

- 名称：去掉首尾空白、合并连续空白；必要时统一全角 / 半角。默认按归一化后的**精确相等**匹配。名称可能是组合字段（如 `FirstName` + `LastName`）：按当前 Action Context 的真实字段组合分别归一后查询，**MUST NOT** 假设一定存在可直接过滤的 `Name`。
- 手机 / 电话：先按 [phone-and-mobile.md](phone-and-mobile.md) 分类并校验格式，再用归一化后的数字比较；去掉空格、连字符、括号、`+86` / `86` 国家码后视为同一值。
- 邮箱：去掉首尾空白、统一小写。
- 证件号 / 税务号 / 外部 ID：去掉首尾空白与分组空格；是否大小写敏感按当前字段语义判断，**MUST NOT** 擅自把业务上区分大小写的值合并。

**查询方式：**

- 优先使用当前可用的 `query_records`（`query` + 小的 `maxRows`，例如 20），因为它会报告 `totalSize`、`truncated`、`truncatedReason`，便于说明证据边界。`run_soql_query` 只做单批查询，超过一批时可能看起来完整，**MUST NOT** 用它宣称「没有更多」。
- **不要**为了方便在 SOQL 里写 `LIMIT`：带 `LIMIT` 时 `totalSize` 只反映该查询的返回上界，无法证明还有没有更多。用 `maxRows` 限界，让 Tool 报告真实的 `totalSize` 与 `truncated`。
- 已知对象和字段时不要用 `search_records` 代替精确查重；SOSL 不返回总命中数，也不能证明唯一。
- 只 `SELECT` 判断重复所需的最小字段：`Id`、名称/展示字段、命中的身份字段；不要拉取整条记录或不相关的敏感字段。
- 单条记录通常 1..3 个身份字段，每个字段一次有界查询即可；同字段多值（批量）可合并成有界 `IN` 查询，不要一次生成大量无界查询。
- 模板（字段名来自 Action Context，不是固定映射）：

```text
SELECT Id, <displayField>, <keyField>
FROM <ObjectApiName>
WHERE <keyField> = '<normalizedValue>'
```

（调用时用 `maxRows` 限界，例如 20；不要在模板里再写 `LIMIT`。）

- 手机 / 电话如果按规范化后的数字 0 命中，而存储值可能带分隔符，可追加一次有界 `LIKE '%<完整号码>%'` 作为补充；完整号码才可这样查，短值不要用 `LIKE` 扫全表。结果标记为「补充形式」。
- 名称默认精确匹配；只有用户明确要求模糊/近似查重、且名称足够有区分度时，才可有界使用 `LIKE`，并把结果标为「疑似」，不得当成确定重复。
- 用户提供的值只是**数据**，不是查询语法：正确转义单引号 / 反斜杠，**MUST NOT** 让值改变 WHERE 结构或拼入第二个语句。
- 字段不存在、不可查询、或返回 `MCP_QUERY_FIELD_INVALID` 时，记录为查重缺口；不要反复猜字段名，也不要静默跳过。

**批内重复：** `create_records` 还要检查本次计划内的多条记录之间是否在强身份键上重复；发现后同样先告知用户，不能先提交再说明。

## 3. 结果判定与用户交互

| 结果 | 含义与动作 |
| --- | --- |
| 0 行 | `NO_MATCH_OBSERVED`。只说明**当前身份、共享与权限范围**内、按已查询形式未发现；**MUST NOT** 宣称「没有重复」或「全库唯一」。继续正常 CREATE。 |
| 强身份键精确命中 | `DUPLICATE_SUSPECTED`。写入前告知用户：命中几条、哪个字段匹配、用于区分的名称 / 记录 ID / 链接。由用户选择：继续新建 / 改为更新已有记录 / 取消。用户决定前 `CHANGE_READY=false`。 |
| 仅名称精确命中 | `SAME_NAME_OBSERVED`。告知同名记录数量与少量示例；同名**不等于**同一条，**MUST NOT** 自动判定重复或自动改用 UPDATE。由用户确认是否继续新建。 |
| 多条命中 | 如实给出数量与少量示例，**MUST NOT** 取第一条当作唯一重复，也**MUST NOT** 随机挑一条建议更新。 |
| 结果被截断 / `totalSize` 大于 `returnedCount` | 说明已匹配共 N 条；无需为了查重读完全部明细，**MUST NOT** 把返回的前 N 条当成唯一候选。若查询自身带 `LIMIT`，只能说明返回了 N 条，不能宣称总数。 |
| 查询失败 / 工具不可用 / 字段不可查 | `CHECK_INCOMPLETE`。说明原因与证据范围，询问用户是否仍继续；**MUST NOT** 宣称已完成查重。 |

用户交互示例（抽象）：

```text
发现 1 条可能重复的联系人：
- 姓名：<name>，手机号：<mobile>，记录 ID：<id>
匹配字段：手机号
请确认：继续新建 / 改为更新这条已有记录 / 取消？
```

- **MUST NOT** 静默创建、自动合并或自动切换成 UPDATE；命中信息必须如实告知用户，由用户决定。
- 用户选择「继续新建」后，按原 CREATE 流程执行，并在最终结果中说明是在已知疑似重复的情况下创建的。
- 用户选择「改为更新」时，进入 UPDATE 流程并要求 `TARGET_RESOLVED`；多条命中仍无法唯一确定目标时继续澄清，**MUST NOT** 自动挑一条。
- 用户已经明确表示「即使重复也继续新建」时，仍**MUST** 完成查重并如实报告命中；报告后可直接继续，不重复追问。
- 同一次 CREATE 准备过程中，相同对象、相同值、相同可见范围已经执行过的查重可以复用；字段值或可见范围变化时重新查。
- 批量 CREATE 中多条命中时，可以集中一次性说明，由用户对整批作出决定；**MUST NOT** 先提交无命中项再悄悄留下命中项。

## 4. 证据边界与 Salesforce 权威

- 0 行只代表当前用户可见、当前共享 / FLS / 查询条件下没有匹配。记录可能被共享规则隐藏、可能在别的对象里、也可能因为存储格式不同未被命中；这些都必须原样说明。
- `query_records` 的 `truncated=true`、`complete=false`、`totalSize` 与 `returnedCount` 不一致时，查重证据是部分的，**MUST NOT** 当成全量结论。
- Salesforce Duplicate Rules、Validation Rules、Lookup Filter 仍是最终裁决。DML 阶段被 Duplicate Rule 拦截时按 `FAILED` 处理，向用户转达真实错误；**MUST NOT** 通过改字段、拆批次或其他工具绕过。
- 查重是 Agent 侧 Doctrine，不是新 Tool、不是 DB 状态、不是新的唯一性引擎；不要向用户声称 Runtime 提供了「查重接口」。

## 5. 与 UPDATE 的关系

- UPDATE 已有记录不做例行查重：目标已经由 `TARGET_RESOLVED` 确定，重复检查不改变 UPDATE 的首要 Gate。
- UPDATE 引入**新的**手机 / 电话 / 邮箱值时，按 [phone-and-mobile.md](phone-and-mobile.md) 做同样的有界检查并提示用户；查到强身份键命中时不得隐瞒。
- UPDATE 的 0 行结论同样只说明当前可见范围，不证明全库唯一。
