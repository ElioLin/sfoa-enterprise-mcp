# 降级与 `INDETERMINATE`：缺口要说出来，不要补上去

诊断工具的价值有一半在「读到了什么」，另一半在**「没读到什么、为什么」**。一个诚实的缺口，用户能拿去找人补前提；一个被补平的缺口，会让用户以为已经查过了。

所以本 Skill 把「如实转述」当作独立的一条规则：**不可用不是没有异常，不确定不是健康。**

## 状态字面量的含义

| 看到的状态 | 含义 | 业务解释重点 |
| --- | --- | --- |
| 正常读到、有内容 | 该来源在这个窗口内返回了这些条目 | 条目数 + 窗口 + 你引用的是哪一条 |
| 正常读到、**空** | 该来源**确实**是空的（查询真的跑过，表真的没有匹配行） | 「读到了，0 条」——这是事实，不是故障；但要说清它是「查过且为空」 |
| **不可用 / `unavailable` / `UNAVAILABLE`** | 该来源这次**没读到** | 哪一节、缺什么前提（对象不可读？权限缺失？字段被拒？）；以及缺了它，这次结论**少支持了什么** |
| **`INDETERMINATE` / 不确定** | 读到了素材，但**判据不足以判定** | 「素材是这些，但按当前判据无法判定」；**不要**把不确定读成健康，也不要自己挑一个档位 |
| **`totalCount: null`** | 总量不可知 | 「总量未知」；**MUST NOT** 说成 0 |

**空 vs 不可用**是最常被混淆的一对，也是最贵的一对：

- 「这一节 0 条」→ 支持「这个窗口内没有该类事件」。
- 「这一节不可用」→ **不支持**任何关于该类事件的陈述，包括「没有」。

要区分二者，看 Tool 是否**为这一节单独声明了状态**。只在整体上给了一个成功标志、而某一节其实没读到时，那个成功标志 **MUST NOT** 被当作该节的证据。聚合类工具通常会把状态、总数与「截断」都**按节**给出，并对不可用的节把总数置为**空值**——逐节读这三样，不要只读 `entries`。

## 不确定出现在两个位置，含义相同

`INDETERMINATE` 可能出现在两个地方，处理方式一致：**它表示判据不足，不表示任何一端**。

1. **逐条结论的值**：例如字段级归因里 `visible` / `editable` 直接取到「不确定」这个字面值。这不是 `false`，也不等于「没权限」；它表示**某一层证据根本没有被读到**。Tool 会同时给出**来源链**，按链上哪一层缺失去组织回答（哪一层没读到、为什么、要什么才能读到），并把层与层之间的**分歧**单独引用出来。
2. **聚合一节的状态**：见上表。这一节读不到，就不要对这类事件做任何陈述。

共同的规则：不确定 **MUST** 被转述为不确定，并且 **MUST** 附上「缺的是哪一层 / 哪一节」；**MUST NOT** 折成肯定或否定，**MUST NOT** 用「可能」「大概率」把不确定包装成倾向。

## 判据不足时的正确回答

`INDETERMINATE` 出现时，按实际问题自然交代以下必要信息，无需固定三段或展示所有技术状态：

1. **读到了什么**：素材本身（条目、字段值、状态字面量）。这部分是证据，照常引用。
2. **为什么判不了**：哪条判据缺失或不可解析（不认识的取值、缺失的时间字段、无法比对的历史）。
3. **要什么才能判定**：缺的那条证据是什么、哪个 Tool 能提供它、或者需要谁去补什么前提。

> 「这一节返回了 N 条，其中 M 条的判据字段无法解析，因此按当前规则是 `INDETERMINATE`——我不把它读成健康。要判定需要能看到该字段的正常取值，目前这个来源没有提供。」

**MUST NOT**：把 `INDETERMINATE` 默认为「大概没事」；**MUST NOT** 挑一个看起来最合理的档位填进去；**MUST NOT** 用「可能」「也许」把不确定包装成结论。

## 判断规则本身的保守性

诊断工具的判定规则（例如「疑似异常」这类档位）是**保守设计**的：不认识的输入落到不确定档，而不是落到健康档。看到不确定档时：

- 那是规则在**按设计工作**，不是工具坏了。
- **MUST NOT** 为了让回答更好看而把不确定档改述成肯定或否定。
- 规则本身在什么条件下会判不出来，属于该 Tool 的契约；以当前 Tool 的输出与 ADR 为准，不以记忆中的规则为准。

## 对称地：不要把「相关」说成「读过」

反过来也要小心：

- 某一节因为**缺少前提**而不可用时，**MUST NOT** 在总结里写「检查了该节，没有发现异常」。
- 有一节不可用、其余节正常时，说明影响本次结论的缺口，不用全局「平台正常」掩盖；无关技术分节可留内部。
- 结论的强度受最弱的一节限制：如果支撑结论的那一节正好不可用，那么结论**MUST** 降级为「未能判定」，而不是照常输出。

## 结构化错误保留为证据，正文解释业务影响

Tool 因为缺前提而拒绝时，返回的是**结构化错误**（错误码 + 缺失前提 + 可行动建议），不是空结果。处理方式：

- 内部保留准确错误码、缺失前提与关联 ID；正文用业务语言说明影响与下一处理方，需要技术细节时准确展开。
- **不要**把结构化错误改写成「没有数据」；「被拒绝」和「读到空」是两回事。
- **不要**在同一个前提上反复重试。缺的东西没变，重试只会得到同一个错误；换成「告诉用户缺什么、请谁去补」。
- 仅在同一可信请求身份下选择其他已启用、授权内证据源，并说明覆盖范围；不得绕过治理、更换执行身份或用别人的证据替代本人的权限裁决。
